# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

BuffPower is a World of Warcraft addon (Lua 5.1 + XML, Ace3) for Mages, Priests and Druids: a PallyPower-style grid of raid groups showing who is missing your class buffs, with click-to-cast buttons. One TOC, [BuffPower.toc](BuffPower.toc), targets three clients through its `## Interface:` list: Classic Era (`11508`), TBC Anniversary (`20505`) and WoW Forever (`16001`, beta). There is no build step or test suite: beyond the luacheck lint, verification means deploying to a client and `/reload`.

## Commands

All scripts are Windows PowerShell and are also wired up as VS Code tasks in [.vscode/tasks.json](.vscode/tasks.json) (Ctrl+Shift+B deploys to all clients).

```powershell
.\scripts\deploy.ps1                                   # deploy to Anniversary (default)
.\scripts\deploy.ps1 -Flavor classic_beta              # WoW Forever beta
.\scripts\deploy.ps1 -Flavor anniversary,classic_beta  # both
.\scripts\install-libs.ps1                             # refresh everything in Libs/ from upstream
```

`deploy.ps1` auto-detects the WoW install (`-WowRoot` or `WOW_ROOT` to override) and mirrors with `robocopy /MIR`. `/reload` picks up Lua/XML changes; TOC changes need a client restart.

`.\scripts\lint.ps1` (VS Code task "Lint") runs luacheck with [.luacheckrc](.luacheckrc), downloading a pinned `luacheck.exe` into the gitignored `.tools/` on first use; [lint.yml](.github/workflows/lint.yml) runs the same check on every push. Run it after editing Lua and keep it at zero warnings. `read_globals` there is a deliberately explicit list of the WoW API the addon uses: when new code calls an API that isn't listed, check it exists on all three clients (or route it through the compatibility layer) before adding it. Luacheck accepts 5.2+ syntax such as `goto` even with `std = "lua51"`, and WoW runs Lua 5.1, so don't rely on it to reject that.

## Release process

Releasing is driven by the TOC version, not by manual tags:

1. Bump `## Version:` in [BuffPower.toc](BuffPower.toc) and rename the matching section in [CHANGELOG.md](CHANGELOG.md) (the packager publishes that file as the release notes).
2. Push to `main`. [auto_tag.yml](.github/workflows/auto_tag.yml) creates a git tag named after that version, and [release.yml](.github/workflows/release.yml) runs the BigWigs packager on it.

A release needs no branch or pull request of its own: commit small releases straight to `main`. Pull requests are for larger pieces of work, and one release can bundle several of them.

Keep `## Version:` an explicit version string: auto-tag reads it literally, so the packager's `@project-version@` keyword would create a tag of that name. A tag containing `beta` or `alpha` becomes a GitHub prerelease. CI does not upload to CurseForge; that is done by hand, choosing which game versions a file applies to.

[CONTRIBUTING.md](CONTRIBUTING.md) repeats the commands, testing constraints, licensing rules and release steps for outside contributors; when one of those changes here, update it there too.

## Libraries are vendored, and must be committed

`Libs/` is committed and [.pkgmeta](.pkgmeta) lists the libraries under `embedded-libraries`, not `externals`, so a release ships exactly the files that were tested locally. Two consequences:

- The packager only ships **git-tracked** files (it ignores everything from `git ls-files --others`). A library on disk but not committed works locally and silently disappears from the release zip.
- The upstream URLs live in [scripts/install-libs.ps1](scripts/install-libs.ps1), not in `.pkgmeta`. Updating libraries means running that script, reviewing the diff, testing, then committing.

Libraries are loaded through [embeds.xml](embeds.xml), not the TOC. A library present in `Libs/` is not loaded unless it is listed there.

## Architecture

Load order (from the TOC): `embeds.xml` → `BuffPowerValues.lua` → `BuffPower.xml` → `BuffPower.lua` → `BuffPowerOptions.lua`. UI strings are plain English literals; there is no locale layer.

- **[BuffPowerValues.lua](BuffPowerValues.lua)** is the data model. `BuffPower_Spells[CLASS][buffKey]` defines each buff with a `single` and optional `group` variant (`spellID`, `rankIDs`, `name`, `icon`) plus `eligibleClasses`. Adding or changing a buff is mostly done here. Spell IDs are TBC-era; `rankIDs` let lower-level characters and lower ranks still be detected. It also holds `BUFFPOWER_DEFAULT_VALUES` (AceDB defaults, no profiles). Settings live in `db.global` (`self.opt`), except group responsibilities and the scroll-wheel player overrides, which are per character in `db.char` (`self.charOpt`).
- **[BuffPower.lua](BuffPower.lua)** is the whole runtime. The flow is: events (`GROUP_ROSTER_UPDATE`, bucketed `UNIT_AURA`, a timer) → `UpdateRoster` builds `raidComposition[group]` → `UpdateBuffStatus` / `UnitHasBuff` scan each member's auras against the spell's name and rank IDs → `UpdateLayout` / `UpdateGroupButton` redraw and rewrite the secure button attributes.
- **[BuffPowerOptions.lua](BuffPowerOptions.lua)** is the AceConfig options UI (per-class buff assignments, group responsibilities).
- **[BuffPower.xml](BuffPower.xml)** only defines the anchor/drag handle and header frames; group and player buttons are created in Lua.

### Secure buttons and combat lockdown

Casting works through `SecureActionButtonTemplate` attributes (`type1`/`spell1`/`unit1` for left click, `*2` for right click). Left click casts the smart choice (group spell, or single-target when the group spell is not learned); right click always casts single-target on a specific player. Attributes, `Show`/`Hide` and layout changes on these frames are forbidden in combat, which is why most update paths start with `if InCombatLockdown() then return end`. Keep that guard on anything that touches a secure frame.

Spells are set by **localized name** from `GetSpellInfo(spellID)`, never by the English `name` field, or casting breaks on non-English clients (see the v1.0.7/v1.0.8 changelog entries).

Out of combat, hovering a group expands its player list through plain Lua (`GroupButton_OnEnter`). In combat, the same expansion is done by secure snippets that run in the restricted environment, set up in `SetUpCombatPlayerLists`: the group button's `_onenter` hides the other groups' lists and shows its own, and player button 1's `_onhide` closes the rest of its list.

### Cross-client compatibility

The top of `BuffPower.lua` holds a compatibility layer, and new API usage should go through it rather than branching on interface numbers:

- `GetSpellInfo` and `IsSpellKnown` prefer the Classic global and fall back to `C_Spell` / `C_SpellBook` (Forever is Mainline-family and lacks the globals). The wrappers keep Classic return signatures. Aura detection uses `AuraUtil.FindAuraByName`, which every client provides.
- `IsSpellInRange` is always normalized to `1`/`0`/`nil`, because callers test `~= 0` and Mainline returns booleans.
- `UnitInRange` returns `nil` (range unknown) instead of Forever's secret boolean. Blizzard's API docs (`Blizzard_APIDocumentationGenerated` on the `forever` branch of wow-ui-source) mark such functions `SecretReturns = true`; check there before testing a new unit API's result.
- Secure snippets are set up unconditionally. Forever beta build 69893 could not compile them (forever-bugs#74, fixed in 70009). Don't detect snippet support by checking `loadstring_untainted`: Blizzard's environment cleanup removes that global on every client before addons load (issue #14). Don't probe by executing a snippet either: on a broken client the failure reaches the error handler even inside `pcall`.

### Forever-specific constraints

Forever shares Mainline's addon restrictions ("addon disarmament"). Aura and unit data can be **secret values** that can't be compared or used as table keys; `C_Secrets.ShouldAurasBeSecret()` reports whether auras are restricted. It is `false` out of combat but `true` in combat, where the aura API refuses addon reads outright ("Auras cannot be accessed when secret while tainted"); `UpdateBuffStatus` then carries each unit's last-read status forward instead of scanning (issue #12). If live in-combat detection is ever needed, the reference approach is Blizzard's `CustomAuraContainerTemplate` (filterable by spell ID), which displays auras without the addon reading them. `.examples/Healium/retail/` (gitignored reference addons; Forever loads it through `Healium_Camelot.toc`, `_Camelot` being Forever's TOC suffix) shows both. It also shows the other secret-safe pattern: let a Blizzard API compute from secret values instead of reading them (`UnitHealthPercent` for the health text). Its aura containers need `## Dependencies: Blizzard_AuraContainer` in the TOC.

## Testing constraints

Changes affecting Classic Era or Anniversary currently can't be verified in-game (only the Forever beta is available to the maintainer, until a subscription planned for around November 2026). Treat anything that alters Classic behaviour as untested until it has been, and release it for Forever only (CurseForge beta file, Forever game version only) until then.

The Unreleased section of [CHANGELOG.md](CHANGELOG.md) carries a "Testing status" line saying which clients the pending changes were verified on. Keep it current: update it when something is tested, and remove it once the Classic and Anniversary tests have passed.
